为什么在这一阶段看 GlobalISel

P1 已用 SelectionDAG 建立基线，回答了带移位的加法怎样匹配到 AArch64 指令。P2 保留相同输入和目标参数，在明确指定 -global-isel 的运行中观察另一条路径。这样可以用同一结果追问两个问题：相同的目标指令在两条路径里是从什么中间表示得到的？怎样用阶段证据确认实际走了哪条路径？

GlobalISel 的通用机器指令可以在翻译、合法化、寄存器组选择和指令选择后分别保存成 MIR。窄例用于对齐两条路径的选择后边界，宽例用于区分合法化拆分和指令选择折叠。SelectionDAG 仍作为对照基线。本节的结论限于固定的 LLVM 版本、目标参数和输入。

总问题

同一个 a + (b << 3) 在两条路径都编译成带移位的 add。你怎样用阶段证据说明两条路径各自做了什么，在哪个边界得到相同的机器指令，并确认 GlobalISel 没有回退？

先看两条路径怎样记录同一条依赖

SelectionDAG 在选择前通过 SDNode 和 SDValue 表示运算与依赖，选择并调度后发出 MachineInstr。GlobalISel 从 IRTranslator 开始就在 MachineFunction 里使用通用 MachineInstr。例如本例的常量、移位和加法分别是 G_CONSTANT、G_SHL、G_ADD。注册 pass 的两个入口可在同一个 AArch64 源文件中对照。LLVM 22.1.8 的 AArch64 pass 配置

怎样读 %26:_(s64)

这是 llc -stop-after=legalizer 保存的 Machine IR（MIR） 中的虚拟寄存器定义。宽例的 .ll 源文件写的是 %shifted = shl i128 %b, 3。生成的 .mir 文件开头可以嵌入一份 LLVM IR，而 body: 下面是机器基本块。形如 %26:_(s64) = G_SHL … 的行出现在 body: 里。

  • %26 是本机器函数里的虚拟寄存器编号。
  • _ 占据寄存器组或寄存器类的标注位置。这一行所在的阶段还没给它指定 register bank 或 class。
  • (s64) 是 GlobalISel 的低层类型（LLT），表示 64 位标量。这里的 s 是 scalar。

窄例能看清格式如何随阶段变化。IRTranslator 后的移位结果写作 %3:_(s64)，RegBankSelect 后写作 %3:gpr(s64)。选择后，融合出来的 ADDXrs 结果写作 %4:gpr64，其中 gpr64 是 AArch64 的寄存器类，%4 仍是虚拟寄存器编号。第一阶段常看的正是选择后的机器指令，因此直接看到了寄存器类的写法。MIR 格式参考 · GlobalISel 通用 MIR

截取位置本次看到什么
IRTranslator 后G_SHL 的结果被 G_ADD 使用。_(s64) 表示通用虚拟寄存器带有低层类型，此时尚未选择 register bank。
Legalizer 后这两条运算仍在，legalized 变为 true。这组输入的运算在这个截点没有拆开。
RegBankSelect 后运算仍是 G_SHL 和 G_ADD，标注变成 gpr(s64)。此处选择的是寄存器组，虚拟寄存器仍存在。
InstructionSelect 后两个通用运算已由一条目标指令 ADDXrs 覆盖，结果标注寄存器类 gpr64。
AArch64 SelectionDAG ISel 后同样看到 ADDXrs。这里应对比 opcode 和操作数形状。这个 dump 的 selected 仍是 false，该字段不能跨路径当作是否已观察到目标指令的判据。

折叠指什么，怎样读 ADDXrs

这里的「折叠」指把移位吸收到加法的第二个操作数里。RegBankSelect 后，G_SHL 产生临时值 %3，由下一条 G_ADD 读取。InstructionSelect 后，移位量 3 成了 ADDXrs 的操作数，原来的移位结果在本例中只供加法使用，因此不需要单独的机器指令来产生它。

RegBankSelect 后
%3:gpr(s64) = G_SHL %1, %2(s64)  // %2 是常量 3
%4:gpr(s64) = G_ADD %0, %3

InstructionSelect 后
%4:gpr64 = ADDXrs %0, %1, 3

最终汇编
add x0, x0, x1, lsl #3

ADDXrs 是 LLVM 对 AArch64 64 位 ADD (shifted register) 的机器 opcode。X 对应 64 位，rs 表示带移位的寄存器形式。lsl #3 修饰第二个输入寄存器 x1，这条指令计算 a + (b << 3) 并保留低 64 位，与本例两条 i64 IR 的结果一致。例如 a = 5、b = 2 时，结果是 5 + 16 = 21。ADD 定义入口 · Xrs 指令形式

先用阶段输出做一次判断。在 RegBankSelect 后还能看到两条通用计算，在 InstructionSelect 后已看到一条目标计算。这一对截点把折叠定位在两者之间。单看最终汇编，无法知道是哪条路径完成了同一件事。完整 GlobalISel 运行启用 -global-isel-abort=1，遇到选择失败就中止，并用 pass 日志核对实际路径。

位宽对照 · 观察合法化怎样拆分宽运算

保持表达式和移位量 3，把所有数据运算从 i64 加宽为 i128。在两条路径中仍使用同一 triple、CPU 和优化级别。完整 i128 IR

define i128 @add_shift_wide(i128 %a, i128 %b) {
entry:
  %shifted = shl i128 %b, 3
  %sum = add i128 %a, %shifted
  ret i128 %sum
}

从 IRTranslator 到 Legalizer

IRTranslator 后仍有 s128 的 G_SHL 和 G_ADD。Legalizer 后，观察到下列 s64 运算。这里 %2/%3 是 a 的低/高半部，%4/%5 是 b 的低/高半部。

%26:_(s64) = G_SHL %4, %25(s64)
%27:_(s64) = G_SHL %5, %25(s64)
%28:_(s64) = G_CONSTANT i64 61
%29:_(s64) = G_LSHR %4, %28(s64)
%30:_(s64) = G_OR %27, %29
%15:_(s64), %21:_(s32) = G_UADDO %2, %26
%17:_(s64), %20:_(s32) = G_UADDE %3, %30, %21

%25 是常量 3。高半部要接收从低半部移出的 3 位，所以右移量是 64 − 3 = 61。G_UADDO 另产出进位 %21，G_UADDE 把它作为高半部加法的输入。这些依赖在合法化截点已可观察。

两条加法怎样传递进位

G_UADDO 和 G_UADDE 都是 GlobalISel 的通用机器指令。G_UADDO 加两个数，产出截断后的和以及无符号进位。G_UADDE 还读取上一段的进位，把它作为 0 或 1 加进去，同样产出和与进位。本例低位用前者，高位用后者。高位的进位 %20 没有使用者，因为原运算只返回低 128 位。通用 opcode 定义

进位的有效信息只有 1 位。LegalizerHelper::narrowScalarAddSub 拆宽加法时先用 LLT::scalar(1) 建立进位值。这个版本的 AArch64 合法化规则对这组 opcode 接受 {s64, s32}（64 位和、32 位进位），并把进位类型的最小宽度限制为 32 位。所以 Legalizer 后看到 %21:_(s32)。s32 是此处 MIR 的表示宽度，进入选好的机器指令后，本例用 NZCV.C 传递这一位。宽运算拆分 · AArch64 合法类型规则

最终汇编的计算extr、adds、adcextr、adds、adc

读懂三个 AArch64 机器 opcode

  1. EXTRXrri 对应 extr x8, x3, x2, #61。把 x3:x2 看作高、低各 64 位的拼接，从整体的第 61 位起取 64 位，得到 (b_hi << 3) | (b_lo >> 61) 的低 64 位。这就是宽移位后的高半部。
  2. ADDSXrs 对应 adds x0, x0, x2, lsl #3。它把 b_lo << 3 和 a_lo 相加，写出低半部，并更新 NZCV。其中 C 保存低半部加法的无符号进位。
  3. ADCSXr 对应助记符 adcs。它计算 a_hi + shifted_b_hi + C，读取输入进位并再次更新 NZCV。ADCXr 对应 adc，执行同样的带进位加法并保留原标志。本例高半部产生的标志不再使用，最终汇编发出 adc x1, x1, x8。

这三个名字是 LLVM 的目标机器 opcode。X 对应 64 位形式，rri 对应两个寄存器输入加立即数，rs 对应带移位的寄存器形式。ADC 和 ADDS 定义 · EXTR 指令格式

EXTR 取哪一段，调度如何保住进位

extr x8, x3, x2, #61 把第一项输入 x3 放在拼接值的高 64 位，把第二项 x2 放在低 64 位。从最低位编号 0 起，截取位 [124:61]。例如 x3 = 1、x2 = 0xA000000000000000 时，结果为 (1 << 3) | 5 = 13。EXTR 不改条件标志。

NZCV 包含四个单比特条件标志。N 是负结果，Z 是零结果，C 是无符号进位，V 是有符号溢出。LLVM 在机器指令里用物理寄存器 $nzcv 建模。本例 ADDSXrs 有 implicit-def $nzcv，ADCXr 有 implicit $nzcv。ADCSXr 同时读入并更新标志。

调度器根据物理寄存器的定义和使用建立依赖边。adds 必须在读取其进位的 adc 前执行，另一条改写 NZCV 的指令也不能移到两者之间而覆盖待用进位。extr 不碰标志，原则上可以与 adds 交换，但必须在 adc 读取它产生的高半部之前。LLVM 机器指令调度的物理寄存器依赖

选择后与最终汇编的截点显示，ADCSXr 与 ADCXr 的差异在 GlobalISel 指令选择之后消失。要找到具体改写的 pass，需要更细的日志边界。

复验 · 同一份 IR，两条路径

从项目根目录运行，工具链用 LLVM 22.1.8。用 case_name=wide 替换第一行，可生成第二组对照。两组产物分别写进 Git 忽略的目录。

case_name=narrow
case "$case_name" in
  narrow) input=experiments/add-shift.ll ;;
  wide) input=experiments/add-shift-wide.ll ;;
esac
out="evidence/day3/$case_name"
mkdir -p "$out"
run_llc() {
  "${LLC:-llc}" -mtriple=aarch64-unknown-linux-gnu -mcpu=generic -O2 \
    -verify-machineinstrs "$@" "$input"
}
for stage in irtranslator legalizer regbankselect instruction-select; do
  run_llc -global-isel -global-isel-abort=1 -stop-after="$stage" \
    -o "$out/$stage.mir"
done
run_llc -stop-after=aarch64-isel -o "$out/selectiondag.mir"
run_llc -debug-pass=Structure -o "$out/selectiondag.s" 2> "$out/selectiondag-pipeline.txt"
run_llc -global-isel -global-isel-abort=1 -debug-pass=Structure \
  -o "$out/globalisel.s" 2> "$out/globalisel-pipeline.txt"

作答后讲解 · 用阶段证据写综合评审

先说明为什么最终汇编不足以判定路径。窄例的两份汇编都发出带移位的 add。GlobalISel 在 RegBankSelect 后仍有 G_SHL 与 G_ADD，InstructionSelect 后已是 ADDXrs。SelectionDAG 的对应证据是 aarch64-isel 后的 ADDXrs。由此可说两条路径在选择后已经对齐到同一指令形态。

再确认实际运行的路径。GlobalISel 的 pass 日志包含 IRTranslator、Legalizer、RegBankSelect 和 InstructionSelect。完整运行加了 -global-isel-abort=1，退出成功，所以这次运行的结果没有经过选择失败后的回退。独立的 SelectionDAG 日志显示 AArch64 Instruction Selection。

用宽例说明结论范围。两条路径最终都发出 adc，但 GlobalISel 选择后仍是 ADCSXr，SelectionDAG 已是 ADCXr。逐 pass 检查 GlobalISel 的机器指令输出，第一次变化发生在 AArch64 Post Select Optimizer 之后。ADCXr 仍读取 NZCV 的进位，少了更新标志的定义。

mkdir -p evidence/day3/wide
"${LLC:-llc}" -mtriple=aarch64-unknown-linux-gnu -mcpu=generic -O2 \
  -verify-machineinstrs -global-isel -global-isel-abort=1 \
  -print-after-all -filter-print-funcs=add_shift_wide \
  experiments/add-shift-wide.ll -o /dev/null 2> evidence/day3/wide/pass-mir.txt

在日志中以 IR Dump After 为边界，找到 ADCSXr 首次变为 ADCXr 的位置。

评审示例。这组实验的最终汇编相同，但运行日志显示走了两条选择路径，且 GlobalISel 的完整运行开启失败即中止并成功退出。窄例的两条路径在选择后均含 ADDXrs。宽例在选择后保留高位加法 opcode 的差异，GlobalISel 的后续优化让两边最终都发出 adc。结论限于这两份 IR 和固定的工具链及参数。
