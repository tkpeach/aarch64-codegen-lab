从 IR 的定义与使用走到目标 matcher

同一个表达式在三个阶段的表示

  1. 构图。SelectionDAGBuilder 访问 IR 指令，把值与依赖转换成带类型的 DAG 节点和边。可以从返回值依赖的计算节点向下追踪操作数。
  2. 整形。SelectionDAGISel 驱动 DAG combine 和 legalization。Combine 重写图形状，legalization 处理目标不直接支持的类型和操作。读匹配规则时，要追踪选择器实际收到的图形状。
  3. 选择。AArch64 selector 把可匹配的子图替换成目标机器节点。一个匹配可以覆盖多层节点。之后机器指令还会经过寄存器分配等 pass，最终由汇编输出展示。

用单独的减法走一遍

define i64 @diff(i64 %a, i64 %b) {
  %d = sub i64 %a, %b
  ret i64 %d
}

从源码可把整数减法追到接收两个 i64 值的 ISD::SUB。llc -print-after=aarch64-isel 的日志标题写着 IR Dump，正文展示的是指令选择后的机器基本块。这个阶段已经同时出现物理寄存器和虚拟寄存器，可以按参数、计算、返回的顺序追踪数据。

bb.0 (%ir-block.0):
  liveins: $x0, $x1
  %1:gpr64 = COPY $x1
  %0:gpr64 = COPY $x0
  %2:gpr64 = SUBSXrr %0:gpr64, %1:gpr64, implicit-def dead $nzcv
  $x0 = COPY %2:gpr64
  RET_ReallyLR implicit $x0
  1. 入口参数。liveins 是 LLVM Machine IR 的通用标记，列出进入这个机器基本块时已有可用值的物理寄存器。在这个入口块，AArch64 调用约定把两个参数放在 $x0 和 $x1，两条 COPY 分别将它们引入虚拟寄存器 %0 和 %1。 调用约定在后端降低函数参数时就确定了物理入口寄存器，所以寄存器分配前也会看到 $x0 和 $x1。分配器随后为 %0、%1 等虚拟寄存器选择实际寄存器，并遵守已有的物理寄存器约束。若源和目标最终落在同一寄存器，入口的 COPY 可以消掉。LLVM MIR 格式参考
  2. 计算。SUBSXrr 读取两个虚拟寄存器，写出 %2，并隐式定义 $nzcv。dead 表示标志位没有后续使用。最终汇编中的计算是 sub x0, x0, x1。
  3. 返回。$x0 = COPY %2:gpr64 把结果放进调用约定规定的返回值寄存器。AArch64 特有的伪指令 RET_ReallyLR 用 implicit $x0 表示返回时需要保留这个结果。最终的 ret 通过链接寄存器 LR（x30）取得返回地址。AArch64 返回指令定义

下一组对照沿用这条数据流。把结果加宽到两个 64 位字后，第二条计算要读取 $nzcv，返回也要通过 $x0 和 $x1 交付两个分量。

受控对照 · 只把减法加宽到 i128

输入仍是一条减法 IR，计算值由 64 位变成 128 位。保持 triple、CPU、优化级别和 selector 配置相同。对照两次选择后的机器指令，再看最终汇编。

define i128 @diff_wide(i128 %a, i128 %b) {
  %d = sub i128 %a, %b
  ret i128 %d
}
%4:gpr64 = SUBSXrr %0:gpr64, %2:gpr64, implicit-def $nzcv
%5:gpr64 = SBCXr %1:gpr64, %3:gpr64, implicit $nzcv

把操作数写成高低两个 64 位字。低半部先计算差，若低半部借位，高半部的差还要减 1。选择后第一条指令定义 $nzcv，第二条隐式读取它。这条依赖在窄减法中没有后续使用，在宽减法中参与计算。最终汇编对应 subs x0, x0, x2 和 sbc x1, x1, x3。

手算一次 0x1_0000000000000000 - 1，把高低半部与两条机器指令对上。这个对照给出了一个边界反例：即使 IR 只有一条算术指令，目标计算仍可能需要多条指令。

1. 构图 · 从 IR 操作数拿到 DAG 值

这里的「DAG 值」是 SDValue，即对一个节点的某个输出的引用。它由生产该值的 SDNode * 和从零开始的结果编号 ResNo 组成。节点描述一次操作，操作数边引用生产节点的具体结果。SDValue 定义

减法节点只产出一个 i64 结果，%d 对应它的结果 0。普通 load 可以同时产出读到的数据和用于约束内存操作顺序的 chain。同一个节点可因此产生两个不同的 SDValue。

SDValue Op1 = getValue(I.getOperand(0));
SDValue Op2 = getValue(I.getOperand(1));

减法规则如何变成匹配表

前面实测的 SUBSXrr 可以追到 AArch64 的这条独立 Pat。左边描述要匹配的 DAG 形状，右边描述要构造的机器节点。$Rn 和 $Rm 把输入绑定到输出指令的对应操作数。AArch64 的减法规则

def : Pat<(sub GPR64:$Rn, GPR64:$Rm),
          (SUBSXrr GPR64:$Rn, GPR64:$Rm)>;

右边的 SUBSXrr 来自 defm SUBS : AddSubS<…> 展开的 Xrr。Defs = [NZCV] 属于指令定义，对应机器指令日志里的隐式定义。生成器把 pattern 转成检查、记录操作数和输出机器节点等 matcher 步骤，再对所有规则一起优化并写表。AddSubS 定义 · matcher 生成过程

用仓库里的 sub-matcher.td 隔离一条形状相同的规则，把输出 opcode 简化为 SUBrr。以下表项由 LLVM 22.1.8 的 llvm-tblgen 实际生成，省略了源模式和目标模式的注释。这张表只包含教学目标的一条规则。完整 AArch64 表会和其他模式一起优化，可能共用 opcode 分派和检查。

/*      0*/ OPC_CheckOpcode, TARGET_VAL(ISD::SUB),
/*      3*/ OPC_RecordChild0, // #0 = $lhs
/*      4*/ OPC_RecordChild1, // #1 = $rhs
/*      5*/ OPC_MorphNodeTo1None, TARGET_VAL(::SUBrr),
                 MVT::i64, 2/*#Ops*/, 0, 1,
    0
  1. OPC_CheckOpcode 检查当前 DAG 根是否是 ISD::SUB。TARGET_VAL 将 opcode 编入表项。
  2. OPC_RecordChild0 和 OPC_RecordChild1 把两个输入 SDValue 存入临时记录的槽位 0、1。它们对应规则里的 $lhs、$rhs。
  3. OPC_MorphNodeTo1None 读取目标 opcode、一个 i64 结果和两个操作数槽位，把当前 DAG 根改写成 SUBrr 机器节点。这里的 None 表示这个表项没有 chain 或 glue 标志。

SelectCodeCommon 按上述顺序读表，记录的操作数直接供机器节点使用。在完整匹配表中，检查失败时可退回到还有备选的匹配作用域，继续试下一条候选。SelectCodeCommon

换一条管线，跟踪同一条依赖

完整输入 · add-shift.ll

define i64 @add_shift(i64 %a, i64 %b) {
entry:
  %shifted = shl i64 %b, 3
  %sum = add i64 %a, %shifted
  ret i64 %sum
}

先看两条路径怎样记录同一条依赖

SelectionDAG 在选择前通过 SDNode 和 SDValue 表示运算与依赖，选择并调度后发出 MachineInstr。GlobalISel 从 IRTranslator 开始就在 MachineFunction 里使用通用 MachineInstr。例如本例的常量、移位和加法分别是 G_CONSTANT、G_SHL、G_ADD。注册 pass 的两个入口可在同一个 AArch64 源文件中对照。LLVM 22.1.8 的 AArch64 pass 配置

怎样读 %26:_(s64)

这是 llc -stop-after=legalizer 保存的 Machine IR（MIR） 中的虚拟寄存器定义。宽例的 .ll 源文件写的是 %shifted = shl i128 %b, 3。生成的 .mir 文件开头可以嵌入一份 LLVM IR，而 body: 下面是机器基本块。形如 %26:_(s64) = G_SHL … 的行出现在 body: 里。

  • %26 是本机器函数里的虚拟寄存器编号。
  • _ 占据寄存器组或寄存器类的标注位置。这一行所在的阶段还没给它指定 register bank 或 class。
  • (s64) 是 GlobalISel 的低层类型（LLT），表示 64 位标量。这里的 s 是 scalar。

窄例能看清格式如何随阶段变化。IRTranslator 后的移位结果写作 %3:_(s64)，RegBankSelect 后写作 %3:gpr(s64)。选择后，融合出来的 ADDXrs 结果写作 %4:gpr64，其中 gpr64 是 AArch64 的寄存器类，%4 仍是虚拟寄存器编号。第一阶段常看的正是选择后的机器指令，因此直接看到了寄存器类的写法。MIR 格式参考 · GlobalISel 通用 MIR

截取位置本次看到什么
IRTranslator 后G_SHL 的结果被 G_ADD 使用。_(s64) 表示通用虚拟寄存器带有低层类型，此时尚未选择 register bank。
Legalizer 后这两条运算仍在，legalized 变为 true。这组输入的运算在这个截点没有拆开。
RegBankSelect 后运算仍是 G_SHL 和 G_ADD，标注变成 gpr(s64)。此处选择的是寄存器组，虚拟寄存器仍存在。
InstructionSelect 后两个通用运算已由一条目标指令 ADDXrs 覆盖，结果标注寄存器类 gpr64。
AArch64 SelectionDAG ISel 后同样看到 ADDXrs。这里应对比 opcode 和操作数形状。这个 dump 的 selected 仍是 false，该字段不能跨路径当作是否已观察到目标指令的判据。

折叠指什么，怎样读 ADDXrs

这里的「折叠」指把移位吸收到加法的第二个操作数里。RegBankSelect 后，G_SHL 产生临时值 %3，由下一条 G_ADD 读取。InstructionSelect 后，移位量 3 成了 ADDXrs 的操作数，原来的移位结果在本例中只供加法使用，因此不需要单独的机器指令来产生它。

RegBankSelect 后
%3:gpr(s64) = G_SHL %1, %2(s64)  // %2 是常量 3
%4:gpr(s64) = G_ADD %0, %3

InstructionSelect 后
%4:gpr64 = ADDXrs %0, %1, 3

最终汇编
add x0, x0, x1, lsl #3

ADDXrs 是 LLVM 对 AArch64 64 位 ADD (shifted register) 的机器 opcode。X 对应 64 位，rs 表示带移位的寄存器形式。lsl #3 修饰第二个输入寄存器 x1，这条指令计算 a + (b << 3) 并保留低 64 位，与本例两条 i64 IR 的结果一致。例如 a = 5、b = 2 时，结果是 5 + 16 = 21。ADD 定义入口 · Xrs 指令形式

先用阶段输出做一次判断。在 RegBankSelect 后还能看到两条通用计算，在 InstructionSelect 后已看到一条目标计算。这一对截点把折叠定位在两者之间。单看最终汇编，无法知道是哪条路径完成了同一件事。完整 GlobalISel 运行启用 -global-isel-abort=1，遇到选择失败就中止，并用 pass 日志核对实际路径。

位宽对照 · 观察合法化怎样拆分宽运算

保持表达式和移位量 3，把所有数据运算从 i64 加宽为 i128。在两条路径中仍使用同一 triple、CPU 和优化级别。完整 i128 IR

define i128 @add_shift_wide(i128 %a, i128 %b) {
entry:
  %shifted = shl i128 %b, 3
  %sum = add i128 %a, %shifted
  ret i128 %sum
}

从 IRTranslator 到 Legalizer

IRTranslator 后仍有 s128 的 G_SHL 和 G_ADD。Legalizer 后，观察到下列 s64 运算。这里 %2/%3 是 a 的低/高半部，%4/%5 是 b 的低/高半部。

%26:_(s64) = G_SHL %4, %25(s64)
%27:_(s64) = G_SHL %5, %25(s64)
%28:_(s64) = G_CONSTANT i64 61
%29:_(s64) = G_LSHR %4, %28(s64)
%30:_(s64) = G_OR %27, %29
%15:_(s64), %21:_(s32) = G_UADDO %2, %26
%17:_(s64), %20:_(s32) = G_UADDE %3, %30, %21

%25 是常量 3。高半部要接收从低半部移出的 3 位，所以右移量是 64 − 3 = 61。G_UADDO 另产出进位 %21，G_UADDE 把它作为高半部加法的输入。这些依赖在合法化截点已可观察。

两条加法怎样传递进位

G_UADDO 和 G_UADDE 都是 GlobalISel 的通用机器指令。G_UADDO 加两个数，产出截断后的和以及无符号进位。G_UADDE 还读取上一段的进位，把它作为 0 或 1 加进去，同样产出和与进位。本例低位用前者，高位用后者。高位的进位 %20 没有使用者，因为原运算只返回低 128 位。通用 opcode 定义

进位的有效信息只有 1 位。LegalizerHelper::narrowScalarAddSub 拆宽加法时先用 LLT::scalar(1) 建立进位值。这个版本的 AArch64 合法化规则对这组 opcode 接受 {s64, s32}（64 位和、32 位进位），并把进位类型的最小宽度限制为 32 位。所以 Legalizer 后看到 %21:_(s32)。s32 是此处 MIR 的表示宽度，进入选好的机器指令后，本例用 NZCV.C 传递这一位。宽运算拆分 · AArch64 合法类型规则

选择后对照 · 相同的低位折叠，略有差异的高位指令

观察位置GlobalISelSelectionDAG

最终汇编的计算extr、adds、adcextr、adds、adc

读懂三个 AArch64 机器 opcode

  1. EXTRXrri 对应 extr x8, x3, x2, #61。把 x3:x2 看作高、低各 64 位的拼接，从整体的第 61 位起取 64 位，得到 (b_hi << 3) | (b_lo >> 61) 的低 64 位。这就是宽移位后的高半部。
  2. ADDSXrs 对应 adds x0, x0, x2, lsl #3。它把 b_lo << 3 和 a_lo 相加，写出低半部，并更新 NZCV。其中 C 保存低半部加法的无符号进位。
  3. ADCSXr 对应助记符 adcs。它计算 a_hi + shifted_b_hi + C，读取输入进位并再次更新 NZCV。ADCXr 对应 adc，执行同样的带进位加法并保留原标志。本例高半部产生的标志不再使用，最终汇编发出 adc x1, x1, x8。

这三个名字是 LLVM 的目标机器 opcode。X 对应 64 位形式，rri 对应两个寄存器输入加立即数，rs 对应带移位的寄存器形式。ADC 和 ADDS 定义 · EXTR 指令格式

EXTR 取哪一段，调度如何保住进位

extr x8, x3, x2, #61 把第一项输入 x3 放在拼接值的高 64 位，把第二项 x2 放在低 64 位。从最低位编号 0 起，截取位 [124:61]。例如 x3 = 1、x2 = 0xA000000000000000 时，结果为 (1 << 3) | 5 = 13。EXTR 不改条件标志。

NZCV 包含四个单比特条件标志。N 是负结果，Z 是零结果，C 是无符号进位，V 是有符号溢出。LLVM 在机器指令里用物理寄存器 $nzcv 建模。本例 ADDSXrs 有 implicit-def $nzcv，ADCXr 有 implicit $nzcv。ADCSXr 同时读入并更新标志。

调度器根据物理寄存器的定义和使用建立依赖边。adds 必须在读取其进位的 adc 前执行，另一条改写 NZCV 的指令也不能移到两者之间而覆盖待用进位。extr 不碰标志，原则上可以与 adds 交换，但必须在 adc 读取它产生的高半部之前。LLVM 机器指令调度的物理寄存器依赖

选择后与最终汇编的截点显示，ADCSXr 与 ADCXr 的差异在 GlobalISel 指令选择之后消失。要找到具体改写的 pass，需要更细的日志边界。

再改一个变量：右移方向藏在哪里？

完整输入 · shift-direction.ll

define i64 @logical(i64 %a, i64 %b) {
  %v = lshr i64 %b, 3
  %r = add i64 %a, %v
  ret i64 %r
}

define i64 @arithmetic(i64 %a, i64 %b) {
  %v = ashr i64 %b, 3
  %r = add i64 %a, %v
  ret i64 %r
}

令 a=0，b 的位模式为 0x8000000000000000。逻辑右移三位得到 0x1000000000000000；算术右移复制最高位，得到 0xf000000000000000。这个输入可以检验两个函数是否被错误地当成同一种运算。再把 b 换成 8，两者都得到 1；只用正数会遗漏这项语义差异。

RegBankSelect 后       InstructionSelect 后         最终汇编中的操作数
G_LSHR → G_ADD         ADDXrs %0, %1, 67          x1, lsr #3
G_ASHR → G_ADD         ADDXrs %0, %1, 131         x1, asr #3

选择后两行的 opcode 一样，区别在最后一个操作数。67 和 131 的低 6 位都是 3，上面的位区分右移类型。沿 AArch64ISelDAGToDAG.cpp 中的 SelectArithShiftedRegister 跟到移位操作数的构造，再用两个汇编操作数检查自己对数值的解释。这个回调说明 DAG 路径的机制，GlobalISel 的边界要另外从 MIR 取证。
