看到最终汇编中的复合运算，怎样证实它在哪一遍出现，并让另一位工程师复验这一判断？

综合产出为一份带有初始预测、相邻 pass 证据、边界反例及续接入口的技术短报告。

  1. 先练习一次有答案的阶段定位
  2. 用消费者检验一个新假设
  3. 把盲预测和核对留在同一份报告

先练习一次有答案的阶段定位

以宽加法为校准。低半部的加法产生进位 C，高半部读取 C。高半部结果返回后，它产生的新进位已经无人读取。如果把这两个方向混在一起，就会误以为省去标志写入也省去了进位输入。

完整输入 · add-shift-wide.ll

define i128 @add_shift_wide(i128 %a, i128 %b) {
entry:
  %shifted = shl i128 %b, 3
  %sum = add i128 %a, %shifted
  ret i128 %sum
}
AArch64 Post Select Optimizer 前
%17 = ADCSXr %3, %30, implicit-def $nzcv, implicit $nzcv
同一 pass 后
%17 = ADCXr  %3, %30,                     implicit $nzcv

两行定义同一个结果，显式输入也相同。按 implicit 与 implicit-def 分开标记读取和写入，再问哪个变化能解释最终的 adc。这个前后对照支持将该函数的改写归到一遍；只有“选择后”和“最终”两张快照时，结论只能定位到两者之间。

从仓库根目录运行，先把 LLVM 22.1.8 的 llc 加入 PATH，或设置 LLC 指向它。

mkdir -p evidence/unit3
"${LLC:-llc}" -mtriple=aarch64-unknown-linux-gnu -mcpu=generic -O2 -verify-machineinstrs -global-isel -global-isel-abort=1 -print-before=aarch64-post-select-optimize -print-after=aarch64-post-select-optimize experiments/add-shift-wide.ll -o evidence/unit3/wide.s 2> evidence/unit3/pair.txt

用消费者检验一个新假设

完整输入 · day6-multiply.ll

define i64 @product_sum(i64 %x, i64 %y, i64 %a) {
  %p = mul i64 %x, %y
  %r = add i64 %p, %a
  ret i64 %r
}

define i64 @product_xor(i64 %x, i64 %y, i64 %a) {
  %p = mul i64 %x, %y
  %r = xor i64 %p, %a
  ret i64 %r
}

两个函数共享 %p = mul i64 %x, %y，更改的是 %p 的唯一消费者。乘法只保留低 64 位。试用 x=3、y=5、a=1 手算两个返回值，在图上标出哪一步使用第三个输入。你要检验的是消费者与乘积能否在目标运算中共同表达，以及这种形态最早在哪个截点可见。

从 AArch64InstrInfo.td 的乘法指令或别名追到它的全部输入，读出每个源寄存器的作用。再到 AArch64InstrInfo.cpp 反查相应机器 opcode 的使用处。记录一个可能发生改写的位置，随后以运行日志检验。若某个操作数是零寄存器，先将零代回算式，再判断第三个 IR 参数是否已经参与运算。

把盲预测和核对留在同一份报告

先填下方第 1、2 栏并保存；再执行这里的命令。按函数名分别抄下选择后的定义、使用者与最终形态。若两端不同，在逐 pass 日志里先搜目标 opcode，再核对同一条指令的操作数是否满足你的判据。记录最早成立的 dump 和它的前一份；若选择时已经成立，报告对应的可观测边界。

从仓库根目录运行，先把 LLVM 22.1.8 的 llc 加入 PATH，或设置 LLC 指向它。

bash experiments/replay-selection.sh 6
"${LLC:-llc}" -mtriple=aarch64-unknown-linux-gnu -mcpu=generic -O2 -verify-machineinstrs -global-isel=0 -fast-isel=0 -filter-print-funcs=product_sum -print-after-all experiments/day6-multiply.ll -o /dev/null 2> evidence/day6/stages.txt

比较时以真实数据依赖对齐。虚拟寄存器号可能被重编号，寄存器分配后还会变为物理寄存器。只搜助记符，或仅比较文本行数，都会把同名但操作数不同的计算混在一起。
